# The in-game overlay

An interactive mod panel drawn inside `EscapeFromTarkov.exe`: press a key, see
what is loaded, click a row to enable or disable it.

Pre-1.0 this would have been forty lines of `OnGUI`. Post-1.0 is IL2CPP, so
there is no `MonoBehaviour` to attach and no managed UI to call into — the
whole BepInEx-era approach, config managers included, has nothing left to load
into. See `docs/IL2CPP.md`.

So the panel is drawn by hand, at the only layer that is still ours: the game
renders through D3D11, and a detour on `IDXGISwapChain::Present` runs once per
frame with the device, the immediate context and the back buffer in hand, after
the game's frame and before the flip. That is the same place Steam, Discord and
RivaTuner draw, for the same reason.

| | where |
|---|---|
| the overlay itself | `abi/aowlspt_overlay.h` (header-only C) |
| the nimony binding | `host/Aowlspt.Overlay/aowloverlay.nim` |
| the test host | `tests/overlayhost/overlayhost.c` |
| the baked font and shaders | generated by `tests/overlayhost/fontgen.c`, `shadergen.c` |

## Why the C is C

Everything here is a function pointer: a COM vtable entry, a detour target, a
detour body with DXGI's calling convention. nimony refuses to `cast` between
`pointer` and `proc` in both directions, which is exactly why `abi/aowlspt_shim.h`
exists — this header is the same layering for the same reason. `aowloverlay.nim`
is the thin part that is worth having in nimony: turn it on, hand it the mod
list, read back a status line.

## How the hook is found

A COM interface pointer is a pointer to a vtable, and every `IDXGISwapChain`
from the same `dxgi.dll` shares one. So the address of the real `Present` can be
read out of *any* swap chain — including a 1x1 one created on a hidden window,
used for nothing and released immediately. `Present` is vtable slot 8 and
`ResizeBuffers` is slot 13, and those indices are fixed by the interface
definition rather than by a build of DXGI.

The alternative — scanning `dxgi.dll` for the bytes of `Present`'s prologue —
depends on a Microsoft DLL that Windows Update rewrites underneath you, and
fails by detouring the middle of an unrelated function. The probe device is ten
lines and is correct by construction.

The detour engine is `abi/aowlspt_detour.h`, unmodified, through
`aowl_hook_install` rather than `aowl_hook_attach`: attach claims a slot in the
fixed pool of assembly thunks that `AowlHostApi.patch` hands to mods, and those
thunks exist to recover arguments for a signature not known at compile time.
The overlay's signatures *are* known, so its detours are plain C functions and
the mod pool stays whole.

## What it draws

One vertex buffer, one shader pair, one draw call. Solid quads and glyphs come
from the same texture — the font atlas carries one fully opaque texel that
rectangles sample — so there is no branch in the pixel shader and no second
pipeline state to set and restore.

The font is 8x16 Consolas, rasterised at build time by `fontgen.c` into a 1-bit
table, and the shaders are DXBC bytecode compiled at build time by
`shadergen.c`. Neither reads a file, wakes GDI, or loads `d3dcompiler` inside
the game process. Regenerate both with `.\build.ps1 -Regen` and paste the
results back into the header; they are checked in so a machine with a different
Consolas cannot silently change the font.

### Render state

Drawing inside `Present` means drawing on a context whose entire state belongs
to the game. The header lists exactly what is saved and restored — IA, VS, PS,
RS, OM, and the geometry/hull/domain shaders, which are the ones people forget:
we never *set* them, but the game's last draw may have left a geometry shader
bound and it would then run on our two triangles. Every D3D11 `*Get*` AddRefs
what it returns, so each one is paired with a `Release`; the version of this bug
that ships leaks one object per frame and reads as "the game leaks memory in
raid".

Not covered, and said plainly: stream-output targets, UAVs bound through
`OMSetRenderTargetsAndUnorderedAccessViews`, and compute state. None affects our
draw, and we never touch them.

### Failure policy

Any unrecoverable error latches `broken`, and from then on both detours are a
straight tail call to the original. The hook stays installed — removing it from
inside itself is its own hazard — and the game renders exactly as it would with
no overlay. `overlayStatus()` says why, in a line meant to be logged verbatim.

## Input

The window procedure is subclassed (`SetWindowLongPtrW(GWLP_WNDPROC)`) on the
swap chain's `OutputWindow`, found on the first frame. Not a `GetMessage` hook:
a message hook only sees what goes through the queue, and both `WM_INPUT` and
anything the game sends itself with `SendMessage` bypass it.

`WM_INPUT` matters specifically. Unity reads the mouse through raw input, so
swallowing `WM_MOUSEMOVE` alone would leave the player spinning the camera while
clicking a button. When the panel is open, raw mouse deltas are integrated into
the overlay's own cursor and the message is consumed — `DefWindowProc` still
sees it, because that is what frees the raw input buffer, but the game's
`WndProc` does not.

The overlay draws its own cursor rather than calling `ShowCursor`: the game
keeps its own show-count in a raid and fighting it leaves the cursor stuck after
the panel closes.

**Limits.** A wndproc subclass cannot intercept `GetAsyncKeyState`, DirectInput,
or `GetRawInputBuffer` polling. If Tarkov reads any input that way, that input
still reaches the game while the panel is open. This is unverified against the
real client — see "risks" in the report.

## The backend

The worker thread polls `GET /aowlspt/mods` and posts
`POST /aowlspt/mods/{guid}/enabled` with `{"enabled":true|false}`. It is the
only thread in this file that blocks; the render thread never does.

With no backend — port 0, or nothing listening — the panel is read-only and
lists what the host pushed in through `overlaySetMod`, which is what is actually
running in this process and the one source that cannot be stale.

The JSON reader is deliberately small and tolerant: it pulls whichever of
`guid`/`id`, `name`, `version`, `enabled` it finds and leaves anything missing
at the host's value, so an unexpected schema degrades to the read-only list
rather than to an empty panel. **The schema is provisional** — it was written
against a stand-in server, not the real routes. If it settles into something
this cannot read, the fix is to parse it in nimony with
`aowl/src/aowlspt/json.nim` and push rows in through `overlaySetMod`, not to
grow the C.

A toggle marks the row `pending` and shows `*`. That is the honest meaning: a
native mod cannot be unloaded from under a running raid, so the button records
what should happen next launch.

## Using it from the client host

```nim
import aowloverlay

# on the host's boot thread, after the mods are loaded -- never from DllMain
if overlayStart(VkInsert, backendPort):
  for m in mods:
    overlaySetMod(m.guid, m.name, m.version, true)
  info "overlay: " & overlayStatus()
else:
  warn "overlay: " & overlayStatus()
```

`overlayStart` returning false is not a reason to fail the host: a missing
overlay is a missing feature, a host that refuses to load over it is a broken
install.

It must not be called from `DllMain`. It creates a window, a D3D11 device and a
thread, and all three deadlock under the loader lock — which presents as the
game hanging on a black screen at startup, not as an error.

## Testing without the game

```
.\build.ps1              # build + headless run, screenshots into tests\overlayhost\shots
.\build.ps1 -Backend     # also run the stand-in backend and check the POST arrives
.\build.ps1 -Interactive # a visible window; INSERT toggles, ESC closes
```

`tests/overlayhost/overlayhost.c` is a D3D11 application that stands in for
Tarkov: a window, a device, a swap chain, a scene, a present loop. The overlay
does not know the difference, which is the point.

Three things it proves rather than merely exercises:

- **The state restore is real.** The scene's pipeline state is set *once*,
  before the loop; every frame after is only Clear + Draw. If the overlay failed
  to put anything back, the scene would stop drawing on frame 2. On top of that
  a fingerprint of the context is compared before and after every `Present`, so
  a mismatch is a failed check rather than something to notice by eye.
- **The pixels are right.** `--shot` reads the back buffer after `Present` into
  a staging texture and writes a BMP. The swap chain uses
  `DXGI_SWAP_EFFECT_SEQUENTIAL` for exactly this reason: under `DISCARD` the
  back buffer after `Present` is undefined.
- **Resize does not break anything.** `ResizeBuffers` is called mid-run and its
  `HRESULT` is checked. Without the overlay dropping its render target view
  first this returns `DXGI_ERROR_INVALID_CALL` — the most common way an overlay
  breaks a game.

`tests/overlayhost/overlaynimtest.nim` covers the other boundary: that nimony
binds the header the way the rest of the repo binds C, that a nimony build needs
no extra link library, and that a nimony `string` survives the trip to
`const char*`.

## What the rest of the tree needs to change

Two things, both outside this directory and neither made here:

1. **`host/Aowlspt.Host.Il2Cpp/aowlhost.nim`** — `import aowloverlay`, then
   call `overlayStart` on the boot thread after the mod loop and
   `overlaySetMod` once per loaded mod.
2. **`tools/aowl.nim`** — add `-p:host\Aowlspt.Overlay` to `buildIl2CppHost`'s
   command so the import resolves, and a `buildOverlayTests` alongside the other
   test builds if the headless run should be part of `aowl test`.

No new link libraries. Everything the header needs from `d3d11.dll` and
`winhttp.dll` is resolved with `GetProcAddress` at runtime; every COM call goes
through a vtable. That is deliberate — an import would make both DLLs load-time
dependencies of a host that is injected into a process mid-startup, where a
failed import is a silent load failure with nothing in the log.
